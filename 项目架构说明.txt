（B）任务/构建调用链（turbo/pnpm scripts 维度）

1. 根目录脚本怎么“调度”各包
- Bee-Design/package.json
  - `utils:build`        -> pnpm -C packages/utils build
  - `components:build`   -> pnpm -C packages/components build
  - `docs:dev`           -> pnpm -C apps/docs-site storybook
  - `turbo:build`        -> turbo run build

2. Turbo 的“自动串联”依赖（来自 Bee-Design/turbo.json）
- `turbo run build` 的规则是：每个包的 build 任务会 dependsOn `^build`
  也就是“先跑它依赖的包的 build，再跑自己”：

packages/utils build
        │
        ▼
packages/components build
        │
        ▼
(如果 docs-site 被纳入 workspace 并定义 build 任务)
apps/docs-site build-storybook

3. components 的 build 里实际做了什么（来自 packages/components/package.json）
- `build` = clean -> build:types(tsc -p tsconfig.build.json) -> build:bundle(rollup ESM/CJS/UMD + build:css)
  - 产物入口：dist/index.esm.js、dist/index.cjs、dist/index.umd.js、dist/index.d.ts、dist/index.css
  - 打包外部依赖：react/react-dom/axios/classnames/lodash/@aozi6666/bee-utils（不打进 bundle）

一、图片里说的 Monorepo 是什么？
Monorepo（单仓多包）= “一个 Git 仓库里放多个彼此独立但可协作的包/子项目”。
常见长相：
- 根目录有 pnpm-workspace.yaml / lerna.json / turbo.json / nx.json 之类的配置
- 下面有 packages/xxx、apps/xxx 等多个 package.json
- 每个包都能单独发布/单独构建，但又能在同一个仓库里共享依赖、共享工具链

它和你平时常见的“一个仓库一个项目”不一样：
- 单仓单包（Single-repo Single-package）：1 个仓库里主要就 1 个可发布的 npm 包（或 1 个应用）
- 单仓多包（Monorepo）：1 个仓库里有 N 个包/应用，彼此引用与协作更紧密


二、我的 Bee-Design 是 Monorepo 吗？
结论：现在是 Monorepo（单仓多包），而且是“轻量、很适合小白”的那种。

我在你的项目里看到的关键信号：
- 根目录有 pnpm-workspace.yaml（说明你用 pnpm workspace 管理多个包）
- 目录里出现了多个 package.json（例如 packages/components、packages/utils，以及 apps 下的文档站点）
- 各个包可以独立构建，但在一个仓库里协作（例如 components 可以依赖 utils 的通用能力）

换句话说：你现在把“组件库（components）+ 通用工具（utils）+ 文档站点（docs-site）”放在同一个仓库里维护。

对小白来说，这种 Monorepo 的价值是：
- 你写组件时能很自然地把可复用逻辑下沉到 utils（并用单向依赖保证不乱）
- 文档站点可以直接依赖 components/源码联动开发，展示效果更接近真实使用


三、Bee-Design 真实采用的架构是什么？
可以理解为：组件库工程化架构（轻量 Monorepo）= “多包源码（packages/*） + 构建（各包独立） + 文档/演示（apps/docs-site） + 测试 + 质量保障”

1）源码层（你写组件的地方）
- packages/components/src
  - React 组件源码、样式、入口导出等（这是你对外发布的组件库包）
- packages/utils/src
  - 通用工具函数（不依赖你自己的组件目录；给多个组件复用）

2）开发调试层（本地开发体验）
- 文档站点 / 演示工程（apps/docs-site）
  - 通过 Storybook / Vite 这类工具把组件跑起来，支持热更新、交互调试

3）构建发布层（把源码变成别人能安装使用的包）
- components 包：Rollup + tsc
  - Rollup：打包输出多种模块格式：ESM / CJS / UMD
  - tsc：生成 types -> dist/index.d.ts（TypeScript 类型声明）
  - styles：生成 dist/index.css，并通过 `./style.css` 导出给使用者显式引入
- utils 包：tsc
  - 直接产出 dist/index.js + dist/index.d.ts（最简单、稳定）

4）组件文档/演示层（给人看的“组件站点/故事集”）
- Storybook（.storybook/ + scripts）
  - storybook：本地预览与展示组件
  - build-storybook：生成静态站点（可部署）

5）测试层（保证组件行为稳定）
- Jest（scripts 里 test/test:ci + jest 配置在 package.json 内）

6）质量与规范层（避免越写越乱）
- ESLint：代码规范与错误检查
- Prettier：统一格式化
- Stylelint：CSS/SCSS 规范
- Husky + lint-staged：提交前自动跑校验，减少“坏代码进仓库”


四、这种架构的优势是什么？（为什么适合做组件库）
1）发布友好：一次构建，输出多种模块格式
- 你的组件库既能被现代打包工具按 ESM 引用，也能兼容需要 CJS 的场景
- UMD 还能给一些 “直接用 script 引入” 或 CDN 场景使用

2）开发效率高：Vite 开发很快
- 本地调试快、热更新快，写组件体验更顺滑

3）展示与协作更清晰：Storybook 把组件“可视化”
- 组件的用法、状态、交互可以被直接看到
- 适合给别人演示，也适合作为“组件说明书”

4）质量更稳定：测试 + 提交前校验
- Jest 能在你改动后帮你发现行为回归
- Husky 能把问题拦在提交前，减少线上/发布后翻车

5）上手门槛相对低（对小白更友好）
- 不需要先理解 workspace、包之间依赖、版本联动、发布流水线等 Monorepo 复杂度
- 先把“组件怎么写、怎么打包、怎么发布”跑通，更容易形成正反馈


五、那我什么时候才需要 Monorepo？
当你出现这些需求时，再考虑升级成 Monorepo 会更合适：
- 你想把“组件库 + 文档站点 + 工具库（utils）”拆成多个包分别维护
- 你希望 docs-site 依赖 components 以“源码联动”的方式开发，而不是拷贝或相对路径 hack
- 你希望把“通用能力”沉到更底层（例如工具函数、DOM 小工具、事件组合工具），让多个组件复用，并且用依赖规则约束：`components -> utils`，避免反向依赖导致耦合
- 你需要多个包独立发布（版本策略、变更日志、CI 流水线）并且团队协作变多

结合你现在 Bee-Design 的实际项目：你已经做了一个“轻量但很稳定”的 Monorepo 形态（最适合小白起步）
- packages/components：对外的 React 组件库包（UI、样式、组件导出）
- packages/utils：纯工具包（不依赖你自己的组件目录；尽量不引样式/业务；只放真正通用的函数）

为什么这种拆法更“稳”？（小白理解版）
- 组件写着写着，总会出现“很多组件都需要的小工具”。如果每个组件都各写一份，就会重复、难维护。
- 但如果把什么都丢进 utils，utils 会变成杂物间，反而更乱。
- 所以正确姿势是：只把“与 UI 无关、能跨组件复用、足够通用”的东西下沉到 utils；组件库只单向依赖 utils。

一个真实的、你项目里已经用上的例子：AutoComplete 复用 clamp
- 之前（手写边界处理）：高亮索引 index 小于 0 就改成 0，大于长度就改成最后一项
- 现在（复用 utils）：把这段规则沉到 `@aozi6666/bee-utils` 里的 `clamp(value, min, max)`，组件里直接调用即可
  - `AutoComplete` 里：`const nextIndex = clamp(index, 0, suggestions.length - 1)`
  - 好处：逻辑更短、表达更清晰；以后别的组件（比如分页、步进器、Slider）也能直接复用同一份规则
